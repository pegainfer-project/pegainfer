# Gemma 4 tensor parallelism

TL;DR: dense Gemma 4 runs as one rank per device: a per-rank weight shard, one `all_reduce` after `o_proj` and one after `down`, and a per-rank KV bound to that rank's own pools. One scheduler thread owns every rank and drives them **concurrently** — rank 0's segment on the scheduler thread, one scoped thread per extra rank, joined at the end of the step (`EngineState::drive_ranks`) — because a step's segment may block on its own device, and a single thread driving the ranks in turn would then be waiting on a peer call it had not issued. 12B bf16 TP2 is verified against a single-rank run; 31B bf16 serves on the 48 GiB-class sm_89 pair (L20/L40S/RTX 6000 Ada) with 8 decode slots and a `PEGAINFER_MAX_CONTEXT` ceiling, measured on two L20s: 57 ms first token, 49.4 ms per step, 143 tok/s at 8 concurrent (`benchmarks/gemma4-31b-tp2-l20.md`). The need is capacity, not the card — ~59.8 GiB of weights do not fit one device under ~60 GiB usable, whatever its model. A cold two-rank process must warm the cuBLAS kernels before the communicator exists, or the first GEMM deadlocks in the driver's module loader. Decode graphs are off under TP: the flag is on by default, so a two-rank launch turns it off and says so, because a captured collective cannot be released while the rank that holds it is stopped inside one (see "Decode graphs are off under TP"). Gate: `engine::lane_gates_tp::the_two_rank_engine_matches_one_rank`.

## What is sharded, and what is not

The text tower's linears split the qwen3 way — output-sharded rows or input-sharded columns — but the head counts differ per layer kind, so the row ranges do too.

| tensor | shard | 12B TP2 (per rank) | 31B TP2 (per rank) |
| --- | --- | --- | --- |
| `q_proj` rows | contiguous query heads, `Q / P` | 8 × 256 | 16 × 256 sliding / 16 × 512 global |
| `k_proj` rows, sliding | `Kv / P` | 4 × 256 | 8 × 256 |
| `v_proj` rows (sliding only) | same as `k_proj` | 4 × 256 | 8 × 256 |
| `k_proj` rows, global | `G % P == 0` → shard, `P % G == 0` → replicate | 1 × 512 (replicated) | 2 × 512 (sharded) |
| `o_proj` cols | the same query-head run | 8 × 256 | 4096 sliding / 8192 global |
| `gate`, `up` rows | `intermediate / P` | 7680 | 10752 |
| `down` cols | `intermediate / P` | 7680 | 10752 |

Published per-rank counts, from each checkpoint's own `config.json` (31B: `Q` 32, sliding `Kv` 16, `G` 4, head dims 256/512, hidden 5376, intermediate 21504, 50 sliding + 10 global layers).

Replicated on every rank: the token embedding (and the tied head), all four layer norms, `q_norm` / `k_norm` (whole heads are held, so the vectors stay whole), `layer_scalar`, and both rope tables. The residual stream and every head width stay whole; only head *counts* and the MLP width shard.

## The world size a shard decision has to satisfy

`TensorParallelConfig::validate_for` refuses a launch that would silently drop or misalign heads. The three counts the kv-cache design doc states are necessary but not sufficient — they do not keep the **per-rank GQA group** integral (`Q = 8`, `Kv = 6`, `P = 2` clears them and yields group `4/3`), so that is checked as well:

```
P  > 0
rank < P
Q  % P == 0
Kv % P == 0
G  % P == 0  ||  P % G == 0
(Q/P) % (Kv/P) == 0          # per-rank sliding group
(Q/P) % G_local == 0         # per-rank global group, sharding branch only
intermediate % P == 0
```

The global check carries a branch condition because only the **sharding** branch can split a group: `G % P == 0` hands a rank `G / P` KV heads, so `(Q/P) / (G/P)` has to be integral. The replicate branch (`P % G == 0`) gives a rank one whole KV head, and `P % G == 0` already keeps its `Q / P` query heads inside that head's group — the `P / G` ranks holding that head split its `Q / G` query heads evenly, so `Q / P` is `(Q / G) / (P / G)`, not a multiple of `Q / G` — so there is nothing left to police, and the check would only compare against a group of one.

A routed (MoE) checkpoint and a W4A16 one are refused under TP > 1: the first needs an expert-sharding design, the second projects whole matrices.

## How a step runs

One scheduler thread owns every rank, but a step drives them **concurrently**: rank 0's segment runs on the scheduler thread and each extra rank's on its own scoped thread, then all are joined (`EngineState::drive_ranks`). One thread per rank is what keeps a host-blocking operation inside a rank's own segment from stranding the others — see "Known bounds" for the stall it fixes. Each rank owns its `DeviceContext`, `GemmaServe` and `StepArena`; a request's KV is **one `GemmaKv` per rank**, each minted from that rank's pools (a `GemmaKv` is pool-bound by construction, so this is what `admit_tokens`' `belongs_to` check requires). `GemmaKv` derefs to rank 0's families, which is why the whole single-rank engine and serve code paths are unchanged.

That per-rank KV is why no host/device split was needed: each rank's entry point advances its own frontier, and because the pools have identical budgets and the admission sequence is identical, the page ids stay in step across ranks.

Per step, each rank's segment calls `activate_rank` (set the device, bind its context, make its thread-local cuBLAS handles current — creating them on first use), runs that rank's segment, and drains it: the extras on their own threads, rank 0 on the scheduler thread before the sampler, which runs on rank 0 alone. The drain is what turns a device fault on a non-primary rank into a named error instead of the primary's collective stalling forever.

Why the extras get threads is the invariant the single-threaded driver could not hold: **a host blocking point must come after every rank's launch.** `all_reduce_rows` enqueues and returns, but a prefill's tower reaches host-side waits of its own — `main`'s stack names one: the gate|up projection GEMM (`cublasGemmEx`, reached from `attention_epilogue_into`) with the thread spinning inside libcuda, and rank 0's per-row readback is the other — so with one thread driving every rank in turn, rank 0 could block on a collective whose peer call had not been issued yet and hang. Running each extra rank's segment on its own thread, and joining only after rank 0's has returned, makes that ordering impossible rather than something each call site has to arrange; it is also what lifted the old prompt ceiling (see "Known bounds").

The staged decode pipeline (ids written by the previous step's sampler) is disabled under TP: a non-primary rank has no sampler and no ids of its own, so every rank takes the explicit-token path.

## The collective

`all_reduce_in_place` on the live extent (`hidden_size × seq_len`) of the projection buffer, inserted in `attention_epilogue_into` after `o_proj` and after `down` — both are row-parallel sums, and both are reduced before the residual they feed is formed. One communicator per rank, built on that rank's compute stream so the reduction lands inside a captured graph once graphs are enabled.

## Cold start: warm the kernels before the communicator

Under the default `CUDA_MODULE_LOADING=LAZY` a fresh process enters the CUDA driver's module loader on the first GEMM of *each shape*. `Comm::from_devices` starts NCCL's proxy threads, which enter that same loader while the communicator comes up; a GEMM that materializes a shape for the first time after that point deadlocks — the engine thread spins at 100% CPU inside `cuLibraryGetModule` (reached through `cublasGemmEx` → `cublasLtTSTMatmul`), never issues rank 1's tower, and the request never returns. It only bites a **cold** process: any run that already did a single-rank pass in the same process (the gate, a warm box) reuses the kernels that pass loaded, which is why it can hide behind a passing gate.

The engine therefore runs one tower pass per rank at load, **before** the communicator is built, at a spread of row counts across cublasLt's kernel-selection regions (`1, 2, 3, 4, 8, …, 1024`, capped by the serving ceiling; larger prompts and every decode bucket reuse those kernels — verified by sweeping sampled prompts of 5…6000 tokens on the geometry it was verified on). With no comm alive the loads happen single-threaded, and that path never touches the loader again. `CUDA_MODULE_LOADING=EAGER` is the equivalent sledgehammer and also works; the warm is preferred because it is per-rank and bounded by the rows the tower actually uses. The cost is a few extra tower passes folded into load — not measured on their own, but the real 31B's cold load is 30 s with them folded in (`benchmarks/gemma4-31b-tp2-l20.md`).

The warm covers the shapes it warms; what it cannot cover is the *class* the driver removes — any host-blocking point inside one rank's segment, whichever call it lands on, including a shape outside the warmed set and the per-row readback (see "Known bounds"). A warmed process that still reaches one is what the concurrent driver answers, so the two are not alternatives: the warm is what makes the *first* pass safe, and the driver is what keeps a later one from stranding the peers.

## Memory: the pools are per-layer arrays

Each family's pool is `layers × pages × bytes-per-page`, which is the number that decides whether a 31B configuration fits a 48 GiB card.

| | local family | global family |
| --- | --- | --- |
| bytes per token | `kv_heads × head_dim × 2 (K,V) × 2` | same |
| 31B TP2 per token | `8 × 256 × 4` = 8 KiB | `2 × 512 × 4` = 4 KiB |
| pages at ceiling 8192 / 16 slots | `15 × 17 + 128 + 1` = 384 | `16 × 128 + 1` = 2049 |
| pool bytes | 50 × 384 × 0.5 MiB = 9600 MiB = 9.38 GiB | 10 × 2049 × 0.25 MiB = 5122.5 MiB = 5.00 GiB |

Every figure here and below is binary (1 GiB = 1024 MiB); the MiB columns are what the start-up log prints, so the two are directly comparable.

31B TP2 therefore needs **29.91 GiB of weights plus 14.38 GiB of pools = 44.29 GiB per rank at the default point**, before the ~0.90 GiB of CUDA context, step arena, cuBLAS workspace and NCCL buffers that the same run reports as the gap between 29.91 GiB of weights and the 14.18 GiB it leaves free on a 44.99 GiB L20. That is **≈45.2 GiB against 44.99 GiB usable**, so the default point does not quite fit — by ~0.2 GiB, not by a wide margin, which is why the reduced envelopes below are the ones that were served. The working envelopes measured on L20:

| ceiling | slots | pools | ≈ resident per rank |
| --- | ---: | ---: | ---: |
| 8192 | 8 | 8.6 GiB | 38.5 GiB |
| 4096 | 16 | 10.3 GiB | 40.2 GiB |
| 2048 | 2 | 1.4 GiB | 31.3 GiB |

The startup error names the page counts when a budget cannot be allocated, and the global pool's size is logged once it is.

The 8192 x 8 row is the one that has been served: 2.50 GiB global pool, 14.18 GiB free after weights, cold load 31.4 s, and 57 ms / 49.4 ms / 143 tok/s (TTFT / step / 8-way aggregate). The full run and method are in `benchmarks/gemma4-31b-tp2-l20.md`.

## What is refused under TP today

`PEGAINFER_ASYNC_PREFILL` (its lane stream cannot be lock-stepped across ranks), `PEGAINFER_GLOBAL_ATTN=tilelang*` (the generated kernels are compiled for the whole global family), `PEGAINFER_PREFIX_CACHE`, and `PEGAINFER_MIX_CHUNK_TOKENS` (a chunked walk's rounds gather across prompts, which the TP gates do not cover). The prompt ceiling that used to be refused here (`PEGAINFER_TP_MAX_PROMPT`) is gone with the hazard it guarded — see "Known bounds".

## Decode graphs are off under TP

`--cuda-graph=true` is the default (as at TP1), and a two-rank launch **turns decode graphs off and logs it** rather than refusing: the flag is on by default, so a refusal would mean no TP2 launch starts until it is flipped, and a launch that cannot start is the worse failure. The reason is **NCCL's abort waits for a captured graph that references the communicator being aborted to be destroyed**, and a rank stopped inside a collective cannot release its own — its graphs live in an arena its own thread holds, and that release is exactly what the abort is holding up. With a captured collective in play the failure path therefore has no order that works: the abort waits for the release, the release runs after the join, and the join waits for the rank the abort was to release. The same cycle runs against rank 0's graphs when an extra rank fails first.

Nothing priced above zero is given up. Capturing against eager is a wash on two L20s at 31B (8192 x 8), back to back on a quiet box — first token 57.0 vs 56.5 ms, decode step 51.5 vs 49.4 ms (+4%), 8-way aggregate 146.0 vs 143.7 tok/s — because the collective, not the launch count, dominates the step; the served envelope above is the 143.7 one. The capture-time constraint the earlier revision documented still holds for the single-rank path (graphs are on there as before): **the kernels must be warm before the communicator exists** (see "Cold start"), or a first-shape GEMM that materializes after `Comm::from_devices` wedges in the driver's module loader. The parity reading the revision before this carried — two ranks captured against one rank eager, `48/48` picks at gap `0.0000` — is not reproducible any more: the env it was taken with turns nothing on. The **TP capture sweep** — the phase-interleaved `precapture_bucket` loop in `start_with_knobs` — is now unreachable and has no runtime; see "Known bounds".
## Verification

`engine::lane_gates_tp::the_two_rank_engine_matches_one_rank` starts a real engine twice — once with one rank, once with two — over the same 12B checkpoint, three prompts and one batch, and compares the requested top-8 logprobs.

It holds the *distributions*, not the greedy tokens: a two-rank reduction sums the same products in a different order and NCCL writes bf16 back, so the logits differ in their last bits and a near-tie can flip the pick. The gate prints the build and the device pair it ran on (`tp2: NCCL 2.18.3, devices 1,2`), because a reading is only comparable with the environment it came from — but nothing here claims *why* two readings from different environments differ. The line comes from this gate's own readings, one procedure, one head (`45eb4a68`, four runs of the 12B on two L20s, `NCCL_PROTO=LL128`):

| claim | result |
| --- | --- |
| one-rank run twice (control) | bit-identical, **asserted** token for token and logprob for logprob, so the comparison is not measuring harness noise |
| steps keeping the one-rank pick | 22 / 24, the same in all four runs |
| worst picked-token logprob gap | 0.5738 (top 0.2362), the same to four decimals in all four runs |
| a differing pick | always a genuine near-tie: each pick inside the other run's top-8, the two picks within `NEAR_TIE_WIDTH` (1.0) of each other in *both* runs' own readings, and both picks' own gaps folded into the bound above before the comparison stops |
| what each half catches | membership rejects a pick outside the other run's top-8; the folded `worst_pick` against `LOGBROB_LINE` catches a flip that wide (both picks' gaps fold in, and a wide flip has moved one of them); the width is the **band between** — a margin just over 1.0 riding a near-zero same-token mean, which the line passes. A unit test fixes one: margins 0.9 and 1.05 with folds of 0.975 |
| the two flips of those 24 steps | their own margins read **0.125 / 0** and **0.375 / 0.5**, i.e. inside `NEAR_TIE_WIDTH` with 2-8x to spare, which is what that width was set from |
| **one `all_reduce` skipped** — the fault the line is for | the gate fails: at request 0 step 0 the one-rank pick leaves the two-rank top-8 (the near-tie rule), and with that rule relaxed the top-token gap reads 2.1895 |

The fault is the `o_proj` reduction commented out in `layer.rs`: both ranks skip it, so the run still completes, and the single-rank control is untouched (at world size 1 the call is a no-op). `worst_pick` reads `0.0000` on that run — the two top-8 lists share no token, so the picked-token bound has nothing left to measure, which is the case the near-tie rule exists to catch — so the rule and the top-token bound are what catch a fault this size, and `LOGBROB_LINE` sits between the two readings instead of under the noise. `LOGBROB_LINE` is `1.0` — it was `0.5`, which sits below this floor and so fails a correct run; 1.0 is ~1.7x over the floor and ~2.2x under the fault, and it is the value `DRIFT_LINE` below already uses. The repo's one precedent for calibrating a quantity of this kind is `serve_oracle`'s `neutral_scale` (two algorithms over one context, 0.31..5.75 observed, line 12.0), i.e. roughly 2x the worst observed drift. What the line is for is a structural error — a wrong shard, a missing reduction, a rank out of step — which moves a logprob by many nats and flips most picks, not 2 of 24; reduction noise is policed by the near-tie rule beside it.

The **shard branch** (`G % P == 0`, which the published 12B never takes — its single global KV head is replicated) is gated with a synthetic checkpoint carrying the real 31B shapes (`Q` 32, `G` 4, head dims 256/512, hidden 5376, intermediate 21504) cut down to six layers, so the whole run is ~8 GiB and takes seconds on any pair. It **measured bit-identical**: 48/48 picks, worst picked-token gap `0.0000`. That is a measurement, not an assertion — the two-rank comparison asserts against `LOGBROB_LINE`, the same line for both branches, so a future run that drifts within the line passes while this sentence's `0.0000` no longer holds.

The gate serves its first prompt on its own and only then the rest as one batch, so the **solo** admission path (`step` + `prefill_extra_ranks`) — where the cold-start hazard above first surfaced, and the only path a lone short request takes — is compared on every run; `PEGAINFER_TP_PROMPTS` / `PEGAINFER_TP_PROMPT_TOKENS` still widen the set. Which branch the gate covers is the checkpoint's: point `PEGAINFER_TEST_MODEL_PATH` at the 12B for the replicate branch, at a 31B-geometry checkpoint for the shard one. **A full-depth 31B cannot be gated against a *single-rank* baseline here**, not for want of a fixture but because the gate needs a single-rank control and 57 GiB of weights do not fit one card — the six-layer synthetic is exactly that shape at a depth that fits. So the numbers above are the 12B (replicate) and the synthetic (shard); the 60-layer real checkpoint is gated instead against its own Hugging Face dump (below) and served end to end on two L20s.

The single-rank suite is unchanged by the TP path (`cargo test --release -p pegainfer-gemma4 --features gemma4 --lib`), and now also carries the prefill-fault gate named above, which runs on one GPU.

The **real 31B checkpoint**, which no single card holds, is served end to end on two L20s; its load, envelope and serving numbers are in `benchmarks/gemma4-31b-tp2-l20.md`.

The fixture is that checkpoint's own dump (`tools/accuracy/dump_gemma4_hf_golden.py`, pinned by file digests), compared over the teacher-forced prompt rows' top-64 logprobs. Measured on two L20s, nine-token prompt:

| claim | result |
| --- | --- |
| reference rows keeping the engine's pick | 7 / 8 |
| worst shared-token logprob gap | 0.6753 |
| the one differing row | a near-tie: the engine's pick sits inside the reference's top-64 |

## Known bounds

- **A step failure stops the engine — whatever rank it happened on, but only with extra ranks.** Rank 0's tower runs on the scheduler thread while each extra rank's runs on its own (see "How a step runs"), so a failure has to release whoever is waiting behind it: rank 0's branch releases its graphs and aborts *every* communicator before the join, and an extra rank's failure is answered by that rank's own thread the same way — rank 0 is the one that would otherwise be waiting inside a collective, and its branch is unreachable until something releases it. Aborting takes the communicator out of its slot, so more than one thread reaching for the same one is a no-op; both failures are fatal (`tp_broken` is set either way) and every later step refuses, so the engine cannot serve a comm-less reduction that would return partial sums. At **world size 1** there is no peer to unblock and no frontier to keep in step, so the same failure stays what it has always been: that one request fails and the driver keeps serving. `engine::lane_gates_logprobs::a_failed_prefill_costs_that_request_not_the_engine` pins the single-rank half on both prefill paths, using a token id outside the embedding — `prepare_single`'s `validate_tokens` refuses it before the tower allocates anything, so the fault needs no injection hook. A gate *does* inject a rank-0 failure at TP2 — `engine::lane_gates_tp::a_failed_rank_zero_segment_stops_the_engine_at_two_ranks`, which shows the engine stops within a deadline rather than wedging — but it is deliberately symmetric: every rank refuses the same prompt before its first collective, so no rank is ever *inside* one when the abort runs, and the release that the abort has to perform is not what that run reaches.
- **The failure path's order is only sound because graphs are off.** The failure path aborts a peer's communicator *while that peer is inside a collective*, and it has to abort it from another thread because the peer cannot release itself. That is free of the reverse dependency only because a TP2 launch turns captured graphs off (`start_with_knobs`; see "Decode graphs are off under TP"): with a captured collective alive, NCCL's abort waits for a graph that only the join can release, and the abort, the join and the release wait on each other. The graph releases the failure path still makes are vacuous while graphs are off — they are there so the order is right if that is ever lifted. What is measured without an engine is the release itself: `engine::lane_gates_tp::an_aborted_communicator_releases_a_waiting_reduction` enqueues a reduction with no peer call, aborts that rank from another thread, and requires its stream to stop waiting — and the abort itself to return — within a deadline. The composition of the two halves (this order, on an engine that captures nothing) is argued rather than exercised: an asymmetric engine-level failure would need a hook the single-rank half also went out of its way not to add.
- **The TP capture sweep has no runtime.** With `start_with_knobs` turning graphs off for every `world > 1` launch, `start_with_knobs`' phase-interleaved `precapture_bucket` loop is unreachable: no gate exercises it, and the parity reading it was built for is gone (see "Decode graphs are off under TP"). It is kept for whoever lifts the disable; unlike the chunked walk above it is not refused, so nothing anywhere stops a run from reaching it if the disable is dropped.
- **The `two_rank` gates run with the graph flag at its default.** `tp2_options` passes `enable_cuda_graph: true`, so every TP gate exercises the turn-off above: a reintroduced *refusal* would fail every one of them at launch instead of going unnoticed.
- **The stall the prompt ceiling guarded was not a length bug — the ceiling is gone with it.** Rank 0's segment reaches a host-side wait inside the tower. An **earlier** capture (a **5-token** prompt) put rank 0's thread in a **lazy cuBLAS/cuBLASLt library load** (`cuLibraryGetModule`, reached through `cublasGemmEx`); the **named** capture — the 12B scored gate at 128 tokens, which hangs 3/3 on `main` — puts it in the **gate|up projection GEMM** (`cublasGemmEx`, reached from `attention_epilogue_into` under `launch_prompt_tower` on the scheduler thread, `gemma4-engine`), spinning inside libcuda with `cuMemsetD8Async` the innermost named frame and nothing below it. In both, rank 0's device reads 100 % busy with rank 1 idle, and the scheduler thread has not reached `step_extra_ranks` — so rank 1's tower was never launched and rank 0's enqueued collectives have no peer, which is the hang itself. Driven **concurrently** (`EngineState::drive_ranks`: rank 0 on the scheduler thread, one scoped thread per extra rank, then join), a host blocking point in one rank's segment cannot stop another rank's launches, so the class is removed rather than bounded and `PEGAINFER_TP_MAX_PROMPT` — with its refusal and its start-up warning — is deleted rather than left as dead scaffolding. Measured on the single-threaded driver with the ceiling lifted: a scored prefill of 50/64/100/128/300 tokens and a 401-token server prefill all complete — on a 4-bit 60-layer geometry, which `validate_for` **refuses at TP2** (`config.rs:228`: TP does not shard the W4A16 GEMMs), so that run predates or bypassed the refusal and **is not reproducible from this tree**; the bf16 31B is not re-measured on the single-threaded driver, and #1115's own record has 128 tokens stalling there. The ceiling was therefore refusing prompts that serve on the geometry it was measured on. Whether the **warm alone** would have been enough for them — which is what decides whether the concurrent driver is needed at all — was then measured on the shipped geometry, on `main`'s single-threaded driver with the warm in place and the ceiling off: a **sampled** prefill of 11 tokens and of **401** tokens both complete on the bf16 12B (35.2 s / 29.7 s), and on the bf16 **31B** the **scored** prompt passes at 64 tokens (472 s) and **hangs at both 128 and 401**, each killed at its 1500 s timeout — with rank 0's device at 100 % and rank 1 idle at the moment the 401-token run was sampled, the same host-wait signature as the capture above. So the warm is not what covers this class, and it is reachable on the geometry this repo serves. A cross-check separates the geometry from the path: the same **scored** gate at the same 128 tokens **also hangs on the 12B** (again rank 0's device at 100 %, rank 1 idle), where the 12B's **sampled** arm passes at 401 tokens — so what differs is the *admission sequence*, not the arm's name: the named block lands in the prompt tower's MLP projection, which **both** arms execute, and which cuBLASLt config that call first touches is whatever the sequence of shapes ahead of it has left alone. It is **not a length bound**: the 31B's scored arm passes at 64 and hangs at 128 and 401, and the 12B's scored arm hangs at 128 in **all three** runs and passes at 401 in **all four**, with the 12B's *sampled* arm passing at both 128 and 401 in the same session. Same arm, same geometry, same session: the outcome is reproducible at each of those lengths and opposite between them, so there is no length to bound — the ceiling was a length bound on a hazard that has none. The **call** rank 0 blocks in is now named (above); why that call spins inside libcuda at one length and not another — the driver-internal reason, which the capture's symbol-less innermost frames do not give — is the open half. The TP gates pass on this build (one-rank comparison `48/48` at gap `0.0000`, the scored probe, the HF reference). The cost is one thread spawn per rank per step, plus the cuBLAS handle pair each step's thread creates in `activate_rank` and destroys when it ends — **~0.8 ms per step** in a standalone copy of that pattern on sm_89. That pair is also what stops the 16.25 MiB per step the first cut leaked (0 MiB growth over a 300- and a 500-step decode run); a thread per rank living for the engine's whole life would keep one pair instead, at the price of that thread.
- **Page-id agreement is inspected, not enforced.** Every rank's pools must stay identical in free-page order — that is the whole basis for "identical page ids". A debug build compares free-page counts after every admission, and every prefill compares the ranks' frontiers; a release build only does the frontiers, and nothing repairs a divergence. Three of the four admission sites self-heal, because the request's `GemmaKv` is dropped and both ranks' pages come back with it; the fourth (`ready_rows_pinned`, which keeps the row in the batch) cannot, so an extra rank that refuses there stops the engine instead of carrying the divergence into a step.
- **The chunked walk's TP code has no runtime.** `PEGAINFER_MIX_CHUNK_TOKENS` is refused under TP (a chunked walk's rounds gather across prompts, which the TP gates do not cover), so the walker's extra-rank admission and its `tp_broken` check are unreachable with a non-empty `more`. Its segments drive the ranks through the same `drive_ranks` as every other path, so nothing but the refusal stands between that code and the gates — untested until one covers it.
- **The mixed step has no TP gate, so the row bound the ceiling carried is back.** `serve::oracle::mixed_step_matches_serial` is single-rank, and the deleted ceiling was also what kept a TP mixed step's prompt rows small (`mixed_fits`, and the gather's `gather_budget`), so both are restored for this step alone: a prompt whose rows do not fit beside the live batch — `TP_MIX_PROMPT_ROWS` (64), counting the live decode rows — is prefilled on its own instead of riding the step, exactly as an over-ceiling prompt was before, and the gather leaves the same room (`PEGAINFER_MIX_GATHER_ROWS` still bounds the gathered rows, and the step rides the same shared segment at every rank). At one rank the step is unbounded, as it always was. That region is still untested at two ranks rather than known-good; the bound stands in for the gate, and both the bound and the knob go when a TP gate covers the step.
- **The vocabulary projection is replicated.** `embed_tokens` and the tied head are `Whole` on each rank (31B: 262144 × 5376 bf16, ~2.8 GiB per rank), and every extra rank computes a whole batch of `vocab × rows` logits per decode step that is then discarded. Dropping it needs a head-free tower for the extra ranks — in graph mode that means a second per-bucket capture, because the head sits inside `decode_gpu_body`. Not implemented, not measured.
- **The long-prompt comparison needs the fixtures' tolerance discipline, not a tighter line.** At one rank the engine matches HF at every *probed* long-context anchor, including the window width: `serve::oracle::context_waypoints_match_hf` passes, reading 1.15 at w1023, **1.48 at w1024** (tolerance 4.61), 3.15 at w1025, 3.80 at w4096, 1.17 at w16384 and 5.23 at w32768 (tolerance 7.65). **At two ranks that depth is unverified**: the 12B golden's `edge` (1024-token) case is not asserted by the TP gates, and running it anyway fails a strict top-64 containment on ~5-8 rows *at one rank as well as at two* — evidence about neither, since a failure both arms share is explained by neither, so it cannot be read as "the second rank adds nothing". What the TP arms do pin at depth is the prefix comparison (a 1024-token prompt's rows against the same prompt's first half): 6.30 at one rank and 9.23 at two, bound by its own control arm (ratio 1.46) and by a count of the rows that share no token at all — those rows never reach `worst`, so the two-rank arm's count is held against the control's own, a ratio with a floor (both arms read **0** of 511 at 1024 tokens; the floor is a sixty-fourth of the compared rows, replacing a flat quarter that let 127 through). The one-rank-vs-two-rank gate's **1.0 line is a 64-token calibration** and cannot hold at depth either: its drift reads 0.57 at 64 tokens, then 1.87 at 512, 4.52 at 768, 5.50 at 256 and 3.81 at 1024 — non-monotone, i.e. the tiling-dependence rather than a threshold. Giving the long cases the tolerance discipline is the follow-up; a strict line at depth is not a detector, it is a flake.
- **`NCCL_PROTO=LL128` is a requirement the code reports rather than enforces.** Startup logs the NCCL version and the effective protocol and warns when it is not LL128; it does not refuse. On this container's stock NCCL the default protocol corrupts the all-reduce buffer (see the operational notes).

## Operational notes

- **A pair, not a card.** Two ranks are two devices; the gate runner claims both (`require_devices 2`, `PEGAINFER_GATE_GPU=a,b`) and exports them as `CUDA_VISIBLE_DEVICES=a,b`, so the ranks inside the process are devices 0 and 1.
- **Set `NCCL_PROTO=LL128` in this container.** With the pod's stock NCCL 2.18.3 (2023, CUDA 12.2 vintage) on CUDA 12.9 and sm_89, the default `LL` protocol — and `SIMPLE` — make the all-reduce kernel write far outside its buffer (`compute-sanitizer` names `ncclKernel_AllReduce_RING_LL_Sum`, ~95 GB past the allocation). A non-primary rank faults asynchronously, so the visible symptom is the primary's collective stalling forever rather than an error. `LL128` is sound, and the repo's own L20 precedent ran NCCL 2.32.3. Prefer a newer NCCL over the variable where the environment allows it.
- **The checkpoint is read once per rank.** 62 GB does not stay in a 32 GB page cache, so a 31B load is ~3.5 min per rank from the PVC and ~15 s from node-local disk — copy it local for iteration.
- **In a container, disable the fabrics NCCL cannot reach** (`NCCL_IB_DISABLE=1`, and `NCCL_P2P_DISABLE=1` if P2P is unavailable). The log otherwise shows `Unable to open device mlx5_*` warnings.
- **Check the pair is healthy.** On a shared box, an uncorrectable DRAM fault shows up as a pair-dependent illegal memory access, which is not a TP defect.
