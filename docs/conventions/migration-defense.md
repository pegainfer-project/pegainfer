# 迁移防御清单：重写类 PR 必须逐条注明旧防御的接班人

> **TL;DR:** 重写/迁移类 PR 的红线——旧实现里每个防御性结构（序号、计数器、等待/超时语义、断言、drop guard）必须逐条给出去向：**继承、替代、或论证废除**。缺一条就是 #830 式补丁螺旋的入场券：18 条 finding 里约三分之一是被当作"实现细节"顺手删掉的旧防御（匿名 key 序号、resolver 负载可见性、tail 等待语义），事后八轮评审逐条补回。

## 清单

迁移/重写 PR 的描述里放一张表，三列：旧防御结构 → 防的失效模式 → 接班人。每行三选一：

1. **继承**：新实现里指出对应物（文件:行）。
2. **替代**：说明新机制如何覆盖同一失效模式。换机制可以，失效模式的覆盖不能断。
3. **废除**：论证该失效模式在新架构下**不可能发生**——依据是结构（类型、所有权、时序），不是"没见它触发过"。

配套两条：

- **测试跟人走**：旧契约测试机制换、断言不换；随 API 删除的测试必须有接棒测试（新路径上断言同一失效模式被挡住）。
- **评审姿势**：看到大段删除，先问"这行防的是什么，谁接班"，再看新代码好不好。防御结构的典型伪装：看似冗余的序号、只增不减的计数、从不超时的等待、永远为真的断言——它们防的是当前代码形态下不会发生、重构后会发生的事。
